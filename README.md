# call me maybe
### _Description_
 
**Call Me Maybe** is a function-calling system built on top of a small local LLM (`Qwen/Qwen3-0.6B`). Given a natural-language prompt and a set of available function definitions, the program outputs the correct function name and a fully-typed, schema-compliant set of arguments — for example, turning *"What is the sum of 40 and 2?"* into:
 
```json
{
  "prompt": "What is the sum of 40 and 2?",
  "name": "fn_add_numbers",
  "parameters": {"a": 40.0, "b": 2.0}
}
```
 
Small models are notoriously unreliable at producing valid JSON on their own. Prompting alone might succeed only a fraction of the time. Instead of hoping the model "gets lucky," this project uses **constrained decoding**: at every generation step, the logits produced by the model are masked so that only tokens which keep the output both **structurally valid JSON** and **compliant
with the function schema** can be selected. Invalid tokens are set to `-inf` before sampling, which guarantees the output is always parseable — regardless of the model's own reliability.

## Algorithm Explanation
 
Constrained decoding works by intervening on the model's logits **before** token selection, at every step of generation:
 
1. The large language model produces raw logits for the entire vocabulary (`get_logits_from_input_ids`).
2. Given the current parser/FSM state, a set of *allowed* token IDs is computed.
3. A numpy array of `-inf` is built over the vocabulary, with `0` placed at each allowed token ID, and added elementwise to the logits. This masks out every token that would break structural or schema validity, without otherwise interfering with the model's own preferences among the tokens that remain valid.
4. The highest-scoring token among the survivors is selected, appended to `input_ids`, and the loop repeats until the JSON object is complete. Only two things are actually generated by the model: the **function name**
and the **parameter values**. The surrounding JSON structure (braces, keys, colons, commas, quotes) is emitted deterministically by the code itself rather than tokenized and generated — there's no ambiguity to resolve there. Instead, the generated **function name** and **parameter values** are stored in a dictionary that gets converted to JSON at the end of the prompt processing. This way, as far as JSON formatting / punctuation goes, that is automatically ensured.
 
The pipeline is split into two complementary strategies depending on what is being generated:
 
- **Function name selection** uses a **character-indexed trie** built from the known function names. Tries are well suited to enumerable, finite string sets: at each step, only the children of the current trie node are valid next tokens, which naturally forces the model to pick a name that exists in the schema.
- **Parameter value generation** determines the current position in a parameter's grammar (e.g. "inside a number, no digits yet," "inside a string, closing quote allowed") by directly **inspecting what has already been written** for that parameter, rather than tracking it through a separate state object. This keeps a single source of truth — the actual generated text — instead of a state machine that could drift out of sync with it. From that inspection, the legal next character class is computed: digits and a terminator for numbers (terminator only once a digit exists) any string content plus an always-available closing quote for strings, and so on. Enum-typed parameters, being finite, are handled with a trie in the same way as function names.

For the function name generation, the generation loop is owned by a `NameGenerator` class (each prompt a new class instance is created), whereas for the parameter values, per value, a `BaseParameterGenerator` child class is instantiated and those instances own the generation loop for their parameter respectively. 

The generation loop these classes own is again as followed: 
it calls `get_logits_from_input_ids` with the growing `input_ids` sequence at every step, applies the appropriate mask (trie-derived, or derived from inspecting the parameter text written so far), and appends the chosen token until the value or name is complete.

A `ConstrainedDecoder` class gets instantiated for the use of the call me maybe program. It only needs the large language model to be used passed, so that model can change (as long as the functions `get_logits_from_input_ids` and `get_path_to_vocab_file` are available, and the Vocab dictionary given follows the type `dict[str, int]`).

## Design Decisions
 
- **Trie vs. inspection-based constraints**: enumerable, closed sets (function names, boolean parameter) use a trie; open-ended types (numbers, strings) derive their legal next characters by inspecting the text already written for that parameter, rather than tracking a separate state machine. This avoids a second source of truth that could fall out of sync with what was actually generated, and matches the shape of each problem: finite sets are naturally a lookup, open-ended values are naturally a "what have I written so far" check.
- **Only meaningful content is generated by the model**: the function name and parameter values go through constrained decoding; the JSON scaffolding around them (braces, keys, punctuation) is written directly by the code. This keeps the model's token budget focused on the only parts of the output that are actually ambiguous, and assures accurate JSON regardless of the function name or parameter accuracy.
- **Vocabulary inversion**: the vocabulary JSON (`{token: id}`) is inverted once, upfront, into `{id: token}`, so the generation loop can do O(1) ID→string lookups instead of scanning the whole vocabulary at every step.
- **Prompt ordering**: the user's question is placed **last**, immediately before generation begins. Putting the function definitions after the question consistently caused the model to select the wrong function; moving the question to the end fixed this and was critical to reaching reliable function-name accuracy.
- **Pydantic v2 validation**: all schema/config classes use `model_validator(mode="after")` rather than custom `__init__` methods, in line with Pydantic v2 idioms and the project's requirement that classes use Pydantic for validation.
- **Termination logic differs by type**: for numbers, structural terminators (comma, closing brace) only become valid once at least one digit has been emitted — letting the model's own logits decide when to stop among the legal options. For strings, the closing quote is valid from the very first step, since an empty string is a legitimate value.

## Performance Analysis
 
- **Function name selection**: On the test set 100% accuracy.
- **Overall accuracy**: The implementation of constrained decoding will always lead to valid JSON output, however the specific value of a parameter (for example what the model outputs for 'regex'), can be wrong semantically.
- **JSON validity**: 100% of outputs are valid, schema-compliant JSON, since only function names and parameters are produced by the LLM. These are stored in a dictionary that then gets outputted to JSON.
- **Speed**: with the encoder from the llm_sdk package it reliably is within the speed limitations of the subject. On my MacBook Pro my bonus encoder is also fast enough, but not always on the PCs at Codam. (On my MBP 35-40s for the test set, whereas using my very basic encoder the program takes 110s of my MBP).

## Challenges Faced
 
- **Bonus encoder**: the bonus encoder was something I had written as one of the first things (wrapping my head around LLMs), but it is a very primitive implementation. It only is able to encode ASCII (because it is byte by byte, and thus multi-byte characters will not be found in the LLM vocab).
- **Vocabulary padding**: the vocabulary file contains 151,643 entries, while the model's logits have a width of 151,936. This mismatch had to be handled explicitly (mapping out-of-range positions correctly).
- **Empty-string generation**: string parameters incorrectly required at least one character before allowing a closing quote. The same rule that is correct for numbers (need at least one digit) but wrong for strings, where an empty string is a valid value.
- **Regex**: it was very challenging to get the LLM to output regex that was somewhat in line with what it actually means. 100% valid REGEX has not been achieved, but a big beginner mistake identified was having the same generation rules for regex as for other string parameters (as regex generation should have access to more types of characters than most strings).
- **Similar output**: the model at times had a tendency to give the same value for two of the parameters of a single function. It was quite challenging thinking of ways to prevent this. Eventually a strategy of both removing used parts of a prompt (ie in the number / integer generation, as well as removing the words of the prompt that share words with the function name) as well as different approaches to prompting were used.


## Testing strategy

I validated my approach using the data.zip file with function definitions and function calling tests provided. I also made my own "edge cases" function calling tests (and the same with changing the function definitions slightly to see how my program would handle other types of parameters). A tip for other people starting this project: keep your function calling tests a short length, otherwise you will have to wait for the entire program to finish all the prompts each time you test, as well as printing your output as it is running, so you can see in real-time which function name and parameters (tokens) are selected / generated.
